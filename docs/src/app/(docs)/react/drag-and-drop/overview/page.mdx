Base UI includes headless drag-and-drop for making elements draggable and building drop zones. It works across mouse, touch, and pen, with pointer-appropriate defaults for starting a drag (see [Activation](/react/components/draggable#activation)). `Draggable.Root` also supports keyboard dragging by default (see [Keyboard navigation](/react/components/draggable#keyboard-navigation)). The components are unstyled, including the preview that follows the pointer.

<DemoShapeSorter />

The two building blocks have their own pages: [Draggable](/react/components/draggable) makes an element a drag source, and [DropTarget](/react/components/drop-target) marks where a drag can be released. The other guides cover [styling](/react/drag-and-drop/styling), [accessibility](/react/drag-and-drop/accessibility), [collections](/react/drag-and-drop/collections) and [testing](/react/drag-and-drop/testing).

## Concepts

**Kinds say what can be dragged where.** Every draggable is of one kind, declared once with `Draggable.createKind`. A drop target lists the kinds it takes in `accept`, and the payload type the kind was created with is what types `source.payload` on every event:

```tsx title="Declaring a kind"
import { Draggable } from '@base-ui/react/draggable';
import { DropTarget } from '@base-ui/react/drop-target';

const card = Draggable.createKind<Card>('card');

<Draggable.Root kind={card} label={cardData.title} payload={cardData} />;

<DropTarget.Root accept={card} label="Done" onDrop={({ source }) => move(source.payload.id)} />;
```

A `createKind` call has unique identity. Declare it once and share the resulting value with every draggable and target in the interaction; two separate `createKind('card')` calls do not match. The name is only a human-readable debugging aid, not an accessible name—that is the `label` you pass to a draggable or a drop target.

If independently evaluated bundles cannot share the same value, use `Draggable.createGlobalKind<Card>('myapp/card')`. Global keys are interned across bundles and hot reloads, so namespace them to your app or package. Reusing one key with incompatible payload types makes unrelated integrations match and bypasses TypeScript's payload safety; prefer `createKind` everywhere else.

**One manager, no provider.** Registration is global: every source and target on the page joins the same manager, wherever they render. Nothing scopes a drag to a subtree — `accept` is what keeps each feature to its own drops, which is why every target has to declare one — `DropTarget.anyKind` is the explicit way to take everything. `Draggable.PreviewProvider` is not a drag scope; it supplies the React tree custom previews render in.

**Drag and drop is synthetic.** Base UI tracks pointer and keyboard input itself rather than using the browser's HTML5 drag-and-drop, so there is no `dataTransfer`, nothing crosses into other applications, and the preview is an ordinary element you style. An OS file drop is handled by [passing native handlers through `render`](/react/components/drop-target#anatomy).

**Drop targets stack.** A drag can be over several nested targets at once. They arrive innermost-first in `location.current.dropTargets`, and only the innermost receives `onDrop`; ancestors see the drag pass through via `onDragEnter`, `onDrag` and `onDragLeave`. Returning `false` from `canDrop` pops a target off the stack so an ancestor can claim the drop; returning `'reject'` refuses the position outright, and no target resolves there at all.

**A drop can resolve to a value inside a target.** Every record in the stack carries [`getLocalPoint()`](/react/components/drop-target#read-where-in-the-target-the-pointer-landed), the pointer's position inside that target as a fraction of its own box. Use it where the target covers a range and the drop means a point in it — a time on a day column, a position on a track — instead of measuring the element in the handler.

**Every event carries the same location history.** `location.initial` is where the drag began, `location.current` where it is now, and `location.previous` where it was at the prior event, each a pointer position plus the target stack at that moment. Comparing `current` against `previous` is how hover work tells that something changed. On the first event of a drag, `previous` holds the pickup input and an empty stack, so that comparison reads as no movement rather than a jump.

## Setup

You do not need a provider for `Draggable.ClonedPreview` or a draggable with no preview. When you render custom content with `Draggable.Preview`, wrap that part of your app in a `Draggable.PreviewProvider`. Put it inside the context providers the preview needs:

```tsx title="Setting up drag and drop"
import { Draggable } from '@base-ui/react/draggable';

function App() {
  return (
    <ThemeProvider>
      <Draggable.PreviewProvider>
        <Board />
      </Draggable.PreviewProvider>
    </ThemeProvider>
  );
}
```

Custom preview content renders beside the provider's children, so it receives context only from providers **above the nearest `Draggable.PreviewProvider`**. It does not inherit a theme, direction, or store provider placed between that preview provider and an individual draggable. Put another `Draggable.PreviewProvider` inside any local context boundary the preview must retain. The DOM container a preview is injected into does not change this React-context boundary.

## Examples

### Sortable lists

To reorder a list, make each item **both** a drag source and a drop target by passing a `DropTarget.Root` to the `Draggable.Root`'s `render` prop, so both roles land on one element.

```tsx title="An item that is both a source and a target"
import { Draggable } from '@base-ui/react/draggable';
import { DropTarget } from '@base-ui/react/drop-target';

const itemKind = Draggable.createKind<string>('item');

<Draggable.Root
  label={item.label}
  kind={itemKind}
  payload={item.id}
  render={
    <DropTarget.Root
      accept={itemKind}
      label={item.label}
      trackDragOver={false}
      onDrag={({ source, location }) => {
        const { clientY } = location.current.input;
        const previousY = location.previous.input.clientY;
        if (clientY !== previousY) {
          reorder(source.payload, item.id, clientY > previousY);
        }
      }}
    />
  }
/>;
```

### Draggable tabs

Tabs can be reordered without giving up their standard selection behavior. Pointer dragging is constrained to the tab list, and the tab settles into its final slot when dropped. Keyboard activation is left to `Tabs`, so the arrow keys continue to move focus and select a tab; <kbd>Alt</kbd>+<kbd>←</kbd>/<kbd>→</kbd> reorder the focused tab instead. <kbd>Delete</kbd> closes it, selecting its nearest neighbor, and a canceled drag restores the previous order.

### Calendar

A custom [modifier](/react/components/draggable#movement-modifiers) on `Draggable.Root` snaps the drag to the calendar's grid: the nearest day column and 15-minute slot. The preview, the drop hit-test, and the reported input all quantize together, so the preview always shows exactly where the event will land. The drop then commits from the resolved column itself: each day declares [`snap`](/react/components/drop-target#snap-to-steps), so `getSnappedLocalPoint` reads the landed slot with no geometry in the handler. Keyboard movement uses a [`keyboardMovement`](/react/components/draggable#controlling-movement) resolver: ↑ and ↓ move by one slot, ← and → switch days.

<DemoSchedulerWeekView />

### Free dragging

Cards can be placed at absolute coordinates and dropped anywhere. Leave the preview's `offset` at its `'source'` default so it preserves the exact pickup point, constrain the drag to the surface with `restrictToElement`, and commit the new position from `getSnappedLocalPoint({ anchor: 'source' })`. The surface declares no snap steps, so the source-anchored point is not quantized and the card stays exactly where the preview is released. Moving it to the end of the list stacks it over the cards it overlaps.

<DemoFigmaBoard />

### Kanban board

An empty card can stand in where a dropped card will land: the nearest insertion point, rather than wherever the pointer happens to be. `useDragMonitor` reads the pointer on every drag, resolves the closest column and slot, and renders a low-opacity placeholder in that slot so the surrounding cards make room, and the drop is predictable even when the pointer is between columns.
