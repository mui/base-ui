## Usage guidelines

- **Dragging is pointer-only**: Draggable responds only to mouse, touch, and pen input. Anything a user can do by dragging must also work with a keyboard and with clicks or taps that do not require dragging.
- **Build the alternative yourself**: For keyboard moves, add shortcuts on the focused item such as <kbd>Alt</kbd>+<kbd>←</kbd> and <kbd>Alt</kbd>+<kbd>→</kbd>. Also provide a click or tap alternative, such as a "Move to" menu. Keyboard shortcuts alone don't meet the [WCAG requirement for an alternative to dragging](https://www.w3.org/WAI/WCAG22/Understanding/dragging-movements.html). Have the alternatives call the same function as the drop handler so both paths apply the same rules. After a keyboard move, keep focus on the moved item and announce the result in a live region, as the [sortable list](#sorting-a-list) demos do. Draggable doesn't announce moves itself. When a collection component already announces sorting outcomes, use its announcements instead of adding a second live region.
- **Drag handles are not controls**: `<Draggable.Handle>` isn't focusable and has no keyboard behavior. Mark a decorative icon inside it `aria-hidden="true"` rather than the handle itself, and give keyboard users another way to start a move.
- **Drags stay within the page**: Draggable tracks pointer events rather than the browser's native drag and drop. It can't move data between browser windows or receive files from the operating system. See [Native file drops](#native-file-drops).
- **Use it to move items**: Reordering lists, moving items between regions, and positioning items on a canvas are good fits. To pick a value from a list, use a component such as [Select](/react/components/select) instead.

## Anatomy

Import the component and assemble its parts:

```jsx title="Anatomy"
import { Draggable } from '@base-ui/react/draggable';

const item = Draggable.createKind('item');

<Draggable.Provider>
  <Draggable.Viewport>
    <Draggable.CollisionProvider kind={item}>
      <Draggable.Root kind={item}>
        <Draggable.Handle />
        <Draggable.Preview />
      </Draggable.Root>
    </Draggable.CollisionProvider>

    <Draggable.Target accept={item} />
  </Draggable.Viewport>
</Draggable.Provider>;
```

`<Draggable.Root>` is the element the user picks up, and `<Draggable.Target>` is where they drop it. Both need a `<Draggable.Provider>` above them. The provider renders no element of its own.

The remaining parts are optional:

- `<Draggable.Handle>` restricts where a drag can start. See [Drag handle](#drag-handle).
- `<Draggable.Preview>` customizes what follows the pointer. See [Drag preview](#drag-preview).
- `<Draggable.CollisionProvider>` groups items that can be reordered. See [Sorting a list](#sorting-a-list).
- `<Draggable.Viewport>` marks a scroll container that should auto-scroll during a drag. See [Auto-scrolling](#auto-scrolling).

One manager handles every drag on the page, so a `<Draggable.Provider>` doesn't isolate its contents from other providers. The provider does two things. It supplies the default [kind](#kinds-and-payloads) for the parts inside it. It also passes React context to custom previews, so place it inside any context providers a custom preview reads.

## Kinds and payloads

A kind identifies a type of draggable item. Create one with `Draggable.createKind`, pass it to the `kind` prop of a `<Draggable.Root>`, and list it in the `accept` prop of the targets that take it. A target ignores drags of any other kind.

The type argument of `createKind` sets the type of the item's `payload`. The payload is any value you attach to a draggable. Handlers read it as `eventDetails.source.payload` on the source and on every target and monitor that accepts the kind.

```tsx title="Declaring a kind with a payload"
const card = Draggable.createKind<string>('card');

<Draggable.Root kind={card} payload={id} />;
<Draggable.Target
  accept={card}
  onDraggableDrop={(eventDetails) => move(eventDetails.source.payload)}
/>;
```

A kind declared with a payload type requires the `payload` prop. Omit the type argument when the kind alone identifies the item:

```tsx title="A kind without a payload"
const divider = Draggable.createKind('divider');

<Draggable.Root kind={divider} />;
```

Base UI compares payloads by identity. Prefer a primitive such as an ID, as above. When the payload has to be an object, memoize it so that unrelated re-renders don't replace it. A new object during a drag re-notifies `useActiveDrag` subscribers and discards any `updatePayload` call:

```tsx title="A memoized object payload"
const payload = React.useMemo(() => ({ id, column }), [id, column]);

<Draggable.Root kind={card} payload={payload} />;
```

Each `createKind` call returns a new kind, so two calls with the same name don't match. Declare each kind once, usually at module scope, and share that value between the sources and targets of an interaction. The name is only for debugging.

When you omit both `kind` and `accept`, a source and a target match if they're inside the same `<Draggable.Provider>`. That's enough for a single self-contained interaction such as the demo at the top of this page.

### Matching several kinds

A target, viewport, or monitor can accept an array of kinds. `eventDetails.source.payload` is then a union of their payload types. Use a kind's `matches` method to narrow it:

```tsx title="Accepting two kinds"
const task = Draggable.createKind<Task>('task');
const file = Draggable.createKind<Attachment>('file');

<Draggable.Target
  accept={[task, file]}
  onDraggableDrop={(eventDetails) => {
    if (file.matches(eventDetails.source)) {
      upload(eventDetails.source.payload.mime);
    } else if (task.matches(eventDetails.source)) {
      addTask(eventDetails.source.payload.id);
    }
  }}
/>;
```

Use `Draggable.anyKind` to accept every drag, for example on a trash zone. Its `source.payload` is `unknown` until you narrow it with `matches`.

## Drag events

Drag sources and drop targets call event handlers as a drag progresses. Each handler receives one `eventDetails` object with the drag `source`, the `target` the drag is over, the event `reason`, the native `event`, and the drag `location`. `onBeforeMoveStart` is the exception. It runs before Base UI looks for a target, so its `eventDetails` carry the `source`, the pointer `input`, and `cancel()`.

To type a handler you define separately, use the types on its component's namespace, such as `Draggable.Root.MoveStartEventDetails<Payload>` and `Draggable.Root.MoveStartEventReason`. Target handlers have matching types such as `Draggable.Target.DropEventDetails<SourcePayload, TargetPayload>`. The event details types also take optional type arguments for [drag data](#storing-data-during-a-drag). Monitor and `registerSource` handlers use the `Draggable.Root` types, and `registerTarget` handlers use the `Draggable.Target` ones.

### Drag source events

`<Draggable.Root>` fires the handlers below, in this order. `onTargetChange` and `onMove` repeat as the pointer moves, and when both fire in the same frame, `onTargetChange` runs first:

```tsx title="Following a drag from start to end"
<Draggable.Root
  kind={card}
  payload={id}
  // Fires just before the drag starts. Call `eventDetails.cancel()` to prevent it.
  onBeforeMoveStart={(eventDetails) => {
    if (eventDetails.input.altKey) {
      eventDetails.cancel();
    }
  }}
  // Fires once when the drag starts. The preview exists by then, so you
  // can measure or restyle the source.
  onMoveStart={(eventDetails) => console.log('lifted', eventDetails.source.payload)}
  // Fires when the drop targets under the pointer change.
  onTargetChange={(eventDetails) => console.log('over', eventDetails.target?.payload ?? 'nothing')}
  // Fires as the pointer moves, at most once per animation frame.
  onMove={(eventDetails) => {
    const { clientX, clientY } = eventDetails.location.current.input;
    console.log('at', clientX, clientY);
  }}
  // Fires once when the drag ends, whether it was dropped, released
  // outside a target, or canceled.
  onMoveEnd={(eventDetails) => {
    if (eventDetails.target) {
      console.log('dropped on', eventDetails.target.payload);
    }
  }}
/>
```

Commit a successful drop in `onMoveEnd`. There, `eventDetails.target` is the target that received the drop. It's `null` when the drag was canceled or released elsewhere. `eventDetails.canceled` is `true` for a cancel, such as <kbd>Esc</kbd> or `cancelDrag()`, and `false` for a release. `eventDetails.reason` gives the specific cause. A source can land on targets of any kind, so `eventDetails.target.payload` is `unknown` until you narrow it with the target's [kind](#identifying-a-target). If the handler also clears temporary state, wrap the commit in `try/finally` so the cleanup runs even when the commit throws:

```tsx title="Committing a drop"
<Draggable.Root
  kind={card}
  payload={id}
  onMoveEnd={(eventDetails) => {
    try {
      if (eventDetails.target && columnKind.matches(eventDetails.target)) {
        commitMove(eventDetails.source.payload, eventDetails.target.payload);
      }
    } finally {
      clearDragState();
    }
  }}
/>
```

Apart from `onBeforeMoveStart`, every handler's `eventDetails` also carry a `location` history:

- `location.current` holds the pointer position for this event and the drop targets under it, innermost first.
- `location.previous` is the same information at the previous event. Compare it with `location.current` to detect what changed.
- `location.initial` is where the drag began.
- `location.grabOffset` is the pointer's offset from the source's top-left corner at pickup.

A drag continues if the source element leaves the DOM, for example when a virtualized list unmounts the dragged row. Identify the dragged item by `eventDetails.source.payload`, not by its element. To stop a drag from code, for example after the dragged record is deleted, call [`cancelDrag`](#canceldrag).

To observe every drag on the page rather than one source, use [`useMonitor`](#usemonitor).

### Drop target events

`<Draggable.Target>` fires the handlers below. Their `eventDetails` hold the drag `source` and the same `location` history. `target` means the same as in a source's handlers: the innermost target under the pointer, which is this target or one nested inside it. `currentTarget` is the record of the target running the handler, like `event.currentTarget` in a DOM event:

```tsx title="Reacting to a drag over a target"
<Draggable.Target
  accept={card}
  payload={zone}
  // Fires when the drag moves over this target.
  onDraggableEnter={(eventDetails) => console.log(eventDetails.source.payload, 'entered')}
  // Fires on every animation frame the pointer moves while over this target.
  // Update hover feedback such as drop indicators here.
  onDraggableMove={(eventDetails) => {
    const { clientX, clientY } = eventDetails.location.current.input;
    highlightSlotAt(clientX, clientY);
  }}
  // Fires when the drag moves off this target, or ends.
  onDraggableLeave={() => clearHighlight()}
  // Fires when the drag is released over this target. Only the innermost
  // target under the pointer receives it, and it never fires on a cancel.
  onDraggableDrop={(eventDetails) =>
    move(eventDetails.source.payload, eventDetails.currentTarget.payload)
  }
/>
```

In `onDraggableLeave`, `target` is the innermost target still under the pointer, or `null` when there's none, for example when the drag ends.

`onDraggableStart` fires only if the target is already under the pointer as the drag starts. To observe every drop, whichever target received it, use `onMoveEnd` on the source or on a monitor and check for the `'drop'` reason. When a drag ends on a target, the source's `onMoveEnd` runs first, then the target's `onDraggableDrop`, then each monitor's `onMoveEnd`.

Use `onDraggableEnter` and `onDraggableLeave` together to react to a pause over a target. For example, expand a collapsed group after the drag stays over it for 500ms:

```tsx title="Expanding a group on hover"
<Draggable.Target
  accept={card}
  onDraggableEnter={() => dwellTimer.start(500, () => setExpanded(true))}
  onDraggableLeave={() => dwellTimer.clear()}
/>
```

## Drop targets

`<Draggable.Target>` marks where the user can drop an item. Pass the [kinds](#kinds-and-payloads) it takes to `accept`, and handle the drop in `onDraggableDrop`:

```tsx title="A basic drop target"
<Draggable.Target
  accept={card}
  onDraggableDrop={(eventDetails) => archive(eventDetails.source.payload)}
/>
```

You can nest targets. The innermost target under the pointer that accepts the drag receives the drop. See [Drop target events](#drop-target-events) for the full set of handlers.

### Accepting drops

`accept` filters by kind. For rules that depend on the item being dragged, the target's current state, or [where the pointer is](#drop-position-within-a-target), add `canDrop`. Base UI calls it every time it looks for a target under the pointer. Return `false` to skip this target and let an ancestor receive the drop, or `'reject'` to block the drop on this target, the targets inside it, and its ancestors:

```tsx title="A column with a capacity"
<Draggable.Target
  accept={card}
  canDrop={({ source }) => !column.cards.includes(source.payload) && column.cards.length < limit}
/>
```

Pass `disabled` to turn a target off. See [Nested drop targets](#nested-drop-targets) for how these options interact.

### Identifying a target

Most targets don't need extra data. A target rendered for each row or column can use the row or column directly in its handlers:

```tsx title="A target that knows where it is"
<Draggable.Target
  accept={card}
  onDraggableDrop={(eventDetails) => move(eventDetails.source.payload, zone)}
/>
```

Pass `payload` when other code must identify the target, for example a source or monitor handler that reads `eventDetails.target`. Those handlers read the value as `eventDetails.target.payload`, and the target's own handlers as `eventDetails.currentTarget.payload`:

```tsx title="Identifying the target from its payload"
<Draggable.Target
  accept={card}
  payload={zone}
  onDraggableDrop={(eventDetails) =>
    move(eventDetails.source.payload, eventDetails.currentTarget.payload)
  }
/>
```

A target can also declare its own `kind`. A shared handler can then tell target types apart with `matches`, which also types `target.payload`:

```tsx title="Telling target types apart"
const dayCell = Draggable.createKind<number>('day-cell');

<Draggable.Target kind={dayCell} accept={card} payload={dayMs} />;
```

## Auto-scrolling

Scroll containers don't scroll during a drag unless you opt them in. Render `<Draggable.Viewport>` on each container that should scroll, including nested ones. The board below renders a viewport for each list and slows down the second one.

import { DemoDragAutoScrollHero } from './demos/scrolling-hero';

<DemoDragAutoScrollHero />

A viewport scrolls while the pointer is near one of its edges and more content remains in that direction. It scrolls on the axes whose `overflow` is `auto` or `scroll`. Base UI looks for drop targets again as the content scrolls, so a target that slides under a stationary pointer can receive the drop.

Nesting follows the DOM tree. The innermost viewport scrolls first. An ancestor viewport scrolls on the axes the inner one doesn't use or has scrolled to the end of. In a horizontal board of vertical columns, the board and each column scroll on their own axis.

Pass `disabled` to pause a viewport, for example while a list is filtered. Pass `accept` to scroll only for drags of some kinds. To change the speed, restrict the direction, or scroll something that isn't a scroll container, see the [examples](#auto-scroll-direction).

```tsx title="Auto-scrolling only for cards"
<Draggable.Viewport accept={card} disabled={isFiltered} />
```

### Scrolling the page

The page doesn't scroll during a drag by default. `<Draggable.Viewport>` renders its own element, so it can't stand in for the document. Register `document.documentElement` through [`useManager`](#usemanager) instead, with the same options as the viewport part:

```tsx title="Letting the page scroll vertically"
const manager = Draggable.useManager();

React.useEffect(
  () =>
    manager.registerViewport(document.documentElement, () => ({
      onDragScroll(eventDetails) {
        if (eventDetails.direction === 'horizontal') {
          eventDetails.cancel();
        }
      },
    })),
  [manager],
);
```

Inner viewports take precedence on the axes they use. `overflow: hidden` on `<html>` or `<body>` stops page scrolling on that axis. This includes the scroll lock of a modal [Dialog](/react/components/dialog).

## Testing

A drag is a sequence of pointer events, so a test can drive one. Most of what's worth testing isn't the gesture, though. The drop handler and the keyboard alternative call the same application function. Test that function directly, or through the keyboard path with ordinary Testing Library interactions. Keep a few gesture tests for the wiring between the parts.

### Choosing an environment

jsdom has no layout and no `document.elementFromPoint`, so Base UI can't find a drop target there. A drag in jsdom starts, moves, and ends normally, but it always ends with the `'outside-release'` reason. Use jsdom to test activation, `disabled` and `onBeforeMoveStart`, the lifecycle handlers, `data-dragging`, and the preview. Use a real browser, through Vitest browser mode or an end-to-end tool, to test drops, drag-over styling, sorting, and auto-scrolling.

### Simulating a drag

Use the `pointer` API of `@testing-library/user-event`. Press on the source, move past the activation threshold, then release. Native HTML5 drag events such as `dragstart` don't start a Base UI drag.

```tsx title="A mouse drag"
const user = userEvent.setup();
const card = screen.getByRole('button', { name: 'Write the spec' });

await user.pointer([
  { keys: '[MouseLeft>]', target: card, coords: { x: 0, y: 0 } },
  // This move passes the 5px threshold and starts the drag.
  { coords: { x: 0, y: 40 } },
  { coords: { x: 0, y: 120 } },
]);
// The drag is in progress. Assert on it here, then release.
await user.pointer({ keys: '[/MouseLeft]' });
```

Touch starts a drag after a 250ms hold, so use fake timers to skip it, then switch back to real timers before the move. Dispatch these events directly with `fireEvent`. Keep the same `pointerId` throughout, and fire the move and the release on `document`. Pass `buttons: 1` until the release so the pointer reads as held. jsdom's `PointerEvent` defaults `buttons` to `0`, and Base UI treats a move without a held button as a missed release.

```tsx title="A touch drag"
const touch = { pointerId: 1, pointerType: 'touch', buttons: 1 };

vi.useFakeTimers();
fireEvent.pointerDown(card, { ...touch, clientX: 0, clientY: 0 });
await act(async () => {
  vi.advanceTimersByTime(300);
});
vi.useRealTimers();

fireEvent.pointerMove(document, { ...touch, clientX: 0, clientY: 120 });
fireEvent.pointerUp(document, { ...touch, buttons: 0, clientX: 0, clientY: 120 });
```

### Waiting and asserting

`onMoveStart` and `onMoveEnd` fire synchronously, during the event that triggers them. Movement and drag-over updates run once per animation frame, so wait for them with `waitFor` before the release:

```tsx title="Waiting for drag-over feedback"
await waitFor(() => {
  expect(screen.getByRole('group', { name: 'Done' })).toHaveAttribute('data-drag-over');
});
```

Assert on the data attributes of the source and targets, and on the event details your handlers received. Each handler receives one `eventDetails` object, so read it from `mock.calls[0][0]` and check the properties you need. A successful drop has the `'drop'` reason:

```tsx title="Asserting on a drop"
expect(onMoveEnd).toHaveBeenCalledTimes(1);
const eventDetails = onMoveEnd.mock.calls[0][0];
expect(eventDetails.target?.payload).toBe('done');
expect(eventDetails.reason).toBe('drop');
```

### Cleaning up

Every drag on the page goes through one manager, so a drag left running leaks into the next test. End every drag you start with a release or <kbd>Esc</kbd>. When a test asserts mid-drag, end the drag in `afterEach`.

Restore real timers before the drag moves, as in the touch example. Base UI runs drag updates, and removes the preview after a drop, on animation frames. A frame requested under fake timers never runs once real timers return, so the preview would stay in the document for the rest of the file.

## Examples

### Drag handle

By default, a press anywhere on the element can start a drag. Render `<Draggable.Handle>` inside the root to start drags from the handle only. The rest of the item stays interactive. A draggable uses its first handle and ignores any others.

```tsx title="Dragging by a handle"
<Draggable.Root kind={card} payload={id}>
  <Draggable.Handle>
    <GripIcon aria-hidden="true" />
  </Draggable.Handle>
  {label}
</Draggable.Root>
```

import { DemoDragHandle } from './demos/handle';

<DemoDragHandle />

The handle renders a `<span>` and isn't focusable. Give keyboard users other controls or shortcuts to move the item, as described in the [usage guidelines](#usage-guidelines). The dashboard demos on this page move the focused widget with <kbd>Alt</kbd>+<kbd>←</kbd> and <kbd>Alt</kbd>+<kbd>→</kbd>.

### Disabling a drag

Pass `disabled` to `<Draggable.Root>` to stop users from picking up an item. Clicks and context menus on the element keep working.

```tsx title="A pinned item"
<Draggable.Root kind={card} payload={id} disabled={pinned} />
```

When the decision depends on the gesture itself, for example on which handle the user pressed or on a modifier key, use `onBeforeMoveStart` instead. It fires just before a drag starts. Call `eventDetails.cancel()` to prevent it:

```tsx title="Canceling a drag as it starts"
<Draggable.Root
  kind={card}
  payload={id}
  onBeforeMoveStart={(eventDetails) => {
    if (eventDetails.input.altKey) {
      eventDetails.cancel();
    }
  }}
/>
```

### Storing data during a drag

The `source` and `target` records can hold drag data that one handler writes and later handlers read. Declare its type as the second type argument of `createKind`. Write it with `updateDragData` and read it as `dragData`. It starts as `undefined` on each pickup. Set source data in `onBeforeMoveStart` so it's ready when Base UI looks for targets and renders a custom preview. The data carries over into the drag that follows. A canceled pickup discards it, so the next attempt starts from `undefined`:

```tsx title="Recording the grab position"
const card = Draggable.createKind<string, { grabOffsetX: number }>('card');

<Draggable.Root
  kind={card}
  payload={id}
  onBeforeMoveStart={(eventDetails) => {
    const rect = eventDetails.source.element.getBoundingClientRect();
    eventDetails.source.updateDragData({ grabOffsetX: eventDetails.input.clientX - rect.left });
  }}
  onMove={(eventDetails) => {
    console.log(eventDetails.source.payload, eventDetails.source.dragData?.grabOffsetX);
  }}
/>;
```

To show drag data in a [custom preview](#custom-preview), call `source.renderPreview()` after updating it. To replace the payload itself, call `updatePayload`. Unlike drag data, the new payload stays after the drag ends, until the `payload` prop changes.

### Activation

A pointer press doesn't start a drag right away. By default:

- Mouse and pen start a drag after 5px of movement.
- Touch starts a drag after a 250ms hold with less than 5px of movement. Moving further before that lets the page scroll instead.

Releasing before the threshold keeps the normal click or tap.

import { DemoActivation } from './demos/activation';

<DemoActivation />

Activation only applies to pointer input, so this demo has no keyboard equivalent. In an app, pair each draggable with a keyboard alternative, as described in the [usage guidelines](#usage-guidelines).

Pass `activation` to change the thresholds. It takes one activation method for every pointer type, or a map keyed by `mouse`, `touch`, and `pen`. Unlisted pointer types keep their defaults.

```tsx title="Custom thresholds"
<Draggable.Root
  kind={card}
  payload={id}
  activation={{
    mouse: { type: 'distance', distance: 10 },
    touch: { type: 'press-hold', delay: 150 },
  }}
/>
```

The available methods are:

- `{ type: 'distance', distance }` starts the drag after the pointer moves by that many pixels.
- `{ type: 'press-hold', delay, tolerance? }` starts the drag after the pointer holds still for `delay` milliseconds. Moving more than `tolerance` pixels cancels the gesture. `tolerance` defaults to 5.
- `{ type: 'immediate' }` starts the drag on `pointerdown`. Use it for a canvas tile that the user drags by its whole area. Pressing a nested button, link, or input still doesn't start a drag.
- `{ type: 'double-click' }` starts the drag on a double-click or double-tap. See [Double-click pickup](#double-click-pickup).

Pass an array to allow several methods at once. The first one to complete starts the drag. An empty array disables pickup.

```tsx title="Drag or hold"
<Draggable.Root
  kind={card}
  payload={id}
  activation={[
    { type: 'distance', distance: 12 },
    { type: 'press-hold', delay: 250 },
  ]}
/>
```

Set a pointer type to `false` to turn off pickup for it. Only do this if your app offers another way to do the same thing with that input, such as move buttons that work with touch, or a custom pen gesture. Unlisted pointer types keep their defaults. In an activation array, `false` overrides every method for that pointer type, including double-click and double-tap pickup.

```tsx title="Disable touch and pen pickup"
<Draggable.Root kind={card} payload={id} activation={{ touch: false, pen: false }} />
```

#### Double-click pickup

With `{ type: 'double-click' }`, a mouse double-click picks the item up. It then follows the pointer without a held button and drops on the next click. If that click is the first half of a double-click, Base UI swallows the second half, so the drop doesn't pick the item up again. With touch or pen, the second tap of a double-tap picks the item up while the pointer is still down, and releasing drops it. <kbd>Esc</kbd> or <kbd>Tab</kbd> cancels either gesture.

Combine it with another method to keep drag-to-pick-up as well, or use a per-pointer map to enable it for some pointer types only:

```tsx title="Double-click or drag"
<Draggable.Root
  kind={card}
  payload={id}
  activation={[{ mouse: { type: 'distance', distance: 5 } }, { mouse: { type: 'double-click' } }]}
/>
```

Avoid this method on items whose double-click already opens or edits content. Base UI consumes the click that drops the item, so it doesn't also activate what's underneath.

For these pickups, `eventDetails.reason` in `onBeforeMoveStart` and `onMoveStart` is `'double-click'` instead of `'pointer'`.

### Constraining movement

A drag follows the pointer freely by default. Pass `modifiers` to `<Draggable.Root>` to keep it on one axis, snap it to a grid, or contain it within an element. Modifiers affect both the preview and the point Base UI uses to find drop targets.

```tsx title="Locking a list to one axis"
<Draggable.Root kind={card} payload={id} modifiers={Draggable.restrictToVerticalAxis} />
```

The built-in modifiers are:

- `restrictToVerticalAxis` and `restrictToHorizontalAxis` lock the drag to one axis.
- `restrictToParentElement` keeps the drag inside the source's parent element.
- `restrictToElement(element)` keeps the drag inside any element. It accepts an element, a ref, or a function returning one.
- `restrictToWindowEdges` keeps the drag inside the browser viewport.
- `snapToGrid(size)` snaps the drag to a grid anchored at the pickup point. Pass a number, or `{ x, y }` for a rectangular grid.

Pass an array to apply several modifiers in order. Each one receives the previous one's result:

```tsx title="Combining modifiers"
<Draggable.Root
  kind={tile}
  payload={id}
  modifiers={[Draggable.snapToGrid(20), Draggable.restrictToParentElement]}
/>
```

In the demo below, `restrictToElement` keeps each widget inside the dashed frame. The modifier constrains the drop position too, so the slot outside the frame never activates.

import { DemoContainedDrag } from './demos/containment';

<DemoContainedDrag />

`<Draggable.Preview>` also accepts `modifiers`. These constrain only the preview and run after the root's modifiers. The drop position still follows the pointer. Use them when leaving an area should cancel the drag instead of dropping on the nearest target. For example, a data grid can keep the preview inside the grid, while a release outside the grid cancels the drag.

#### Custom modifiers

A modifier is a function that receives the proposed `point` and returns the point to use. It also receives the `initialPoint` where the drag started, the pointer position `input` before this list of modifiers ran, the source and preview rectangles, the element's `scale`, and the modifier keys held during the current event. It runs on every frame, so keep it cheap.

```tsx title="Snapping to fixed rows"
import { Draggable } from '@base-ui/react/draggable';

const snapToRows: Draggable.Root.Modifier = ({ point }) => ({
  x: point.x,
  y: nearest(ROW_TOPS, point.y),
});
```

Points are in client pixels, matching `getBoundingClientRect()`. On a zoomed or scaled canvas, multiply a canvas distance by `scale` to convert it to client pixels. `scale` is `{ x: 1, y: 1 }` when nothing is scaled.

```tsx title="Moving by 20 canvas units"
const nudgeRight: Draggable.Root.Modifier = ({ point, scale }) => ({
  x: point.x + 20 * scale.x,
  y: point.y,
});
```

The `ctrlKey`, `shiftKey`, `altKey`, and `metaKey` flags let a modifier react to keys held during the drag. Pressing or releasing a key reapplies the modifiers on the next frame.

```tsx title="Snapping to 45° while Shift is held"
const snapToAngle: Draggable.Root.Modifier = ({ point, shiftKey, initialPoint }) => {
  if (!shiftKey) {
    return point;
  }
  const dx = point.x - initialPoint.x;
  const dy = point.y - initialPoint.y;
  const angle = Math.round(Math.atan2(dy, dx) / (Math.PI / 4)) * (Math.PI / 4);
  const distance = dx * Math.cos(angle) + dy * Math.sin(angle);
  return {
    x: initialPoint.x + Math.cos(angle) * distance,
    y: initialPoint.y + Math.sin(angle) * distance,
  };
};
```

### Drag preview

During a drag, a copy of the source element follows the pointer. This clone keeps the element's classes, form values, canvas drawings, and scroll positions. Base UI renders it in the browser's top layer, so no scroll container clips it and nothing on the page paints over it.

The clone has the source's tag and goes at the end of the source's parent, with no wrapper. A dragged `<tr>` is previewed by a `<tr>` in the same `<tbody>`, and an `<li>` by an `<li>` in the same list, so the page stays valid HTML during the drag.

Base UI rewrites the clone's IDs to avoid duplicates in the document. Style it with classes or `[data-drag-preview]` instead of ID selectors. Styles that depend on `:hover` or `:focus` don't apply to it. The clone also leaves out content that lives outside the DOM, such as a WebGL canvas, a playing video, or a shadow DOM. A [custom preview](#custom-preview) is copied the same way, except that it redraws a 2D canvas on every frame, so show a still image of other such content there instead. A custom preview also helps when the source is large enough that cloning it causes a visible delay.

Render `<Draggable.Preview>` without children to configure where the clone appears. In that case it renders no element of its own:

```tsx title="Placing the clone under the pointer"
<Draggable.Root kind={card} payload={id}>
  {label}
  <Draggable.Preview offset="pointer" />
</Draggable.Root>
```

Pass `disabled` to drag without any preview. The drag still runs and targets still respond, which suits a canvas that draws its own feedback:

```tsx title="Dragging without a preview"
<Draggable.Root kind={shape} payload={id}>
  {label}
  <Draggable.Preview disabled />
</Draggable.Root>
```

### Custom preview

Pass children to `<Draggable.Preview>` to show something other than a clone. Keep `pointer-events: none` on the preview so it doesn't block the drop targets under it. The dashboard below drags each widget as a compact badge:

```tsx title="A badge instead of a clone"
<Draggable.Root kind={widget} payload={id}>
  {title}
  <Draggable.Preview className="Badge" offset="pointer">
    <span>{value}</span>
    {title}
  </Draggable.Preview>
</Draggable.Root>
```

import { DemoBadgePreview } from './demos/badge';

<DemoBadgePreview />

Base UI renders the children off-screen, then copies them into an element at the end of the source's parent, the same way it clones a source. The copy follows every later render of the children, so a component inside the preview can hold state or subscribe to the drag with [`useMonitor`](#usemonitor). Field values and 2D canvas drawings are copied on every frame. The copy keeps the children's IDs, unless the page already uses one, in which case it gets a suffix.

Refs inside the preview point at the off-screen elements, which have no layout to measure. The copy has no event handlers, and custom elements in the preview are constructed again for it.

The preview renders a `<div>` by default. Next to a table row or a list item, pass `render` so the preview is valid there. React warns about an invalid preview element in a table or a `<select>`, and Base UI warns in a list:

```tsx title="Previewing a table row"
<Draggable.Root kind={row} payload={id} render={<tr />}>
  <td>{name}</td>
  <Draggable.Preview render={<tr />} className="RowPreview">
    <td>{name}</td>
  </Draggable.Preview>
</Draggable.Root>
```

Pass a function as children to build the preview from the dragged item. It receives the drag `source` and `location` when the drag starts. Return `null` to show no preview.

```tsx title="Building the preview from the payload"
<Draggable.Preview kind={card}>
  {({ source }) => <span className="Chip">{source.payload}</span>}
</Draggable.Preview>
```

Call `source.renderPreview()` from a drag handler to run the function again with the current `source` and `location`. Store what the preview shows with [`updateDragData`](#storing-data-during-a-drag) first:

```tsx title="Showing the drop time in the preview"
const event = Draggable.createKind<string, { time: string }>('event');

<Draggable.Root
  kind={event}
  payload={id}
  onMove={(eventDetails) => {
    eventDetails.source.updateDragData({ time: getTimeAt(eventDetails.location.current.input) });
    eventDetails.source.renderPreview();
  }}
>
  {title}
  <Draggable.Preview kind={event}>
    {({ source }) => <span className="Chip">{source.dragData?.time}</span>}
  </Draggable.Preview>
</Draggable.Root>;
```

Without custom children, `source.renderPreview()` clones the source again, which picks up content the source changed during the drag.

The engine positions the preview through its `margin` and `translate`, so the preview's own `margin` and `translate` shift it from its [offset](#preview-position), the way they would shift it in place. Percentages in `translate` refer to the preview's own size.

A custom preview stays mounted even if the source unmounts during the drag. If its `<Draggable.Provider>` unmounts, it keeps its last content until the drag ends. It reads React context from above the nearest `<Draggable.Provider>`, so place that provider inside any contexts the preview needs.

The preview takes the size of its content. To match the source instead, use the `--drag-source-width` and `--drag-source-height` CSS variables:

```css title="Matching the source size"
.RowPreview {
  width: var(--drag-source-width);
  min-height: var(--drag-source-height);
}
```

### Preview position

Use the `offset` prop to position the preview relative to the pointer. It works the same for the clone and for custom content.

```tsx title="Positioning the preview"
// The default. The preview starts over the source and keeps the grab offset.
<Draggable.Preview offset="source" />

// The preview's top-left corner sits under the pointer.
<Draggable.Preview offset="pointer" />

// A fixed distance from the pointer.
<Draggable.Preview offset={{ x: 12, y: 12 }}>{label}</Draggable.Preview>

// Computed at drag start. This centers the preview under the pointer.
<Draggable.Preview
  offset={({ container }) => ({
    x: container.offsetWidth / 2,
    y: container.offsetHeight / 2,
  })}
>
  {label}
</Draggable.Preview>
```

### Preview container

Base UI inserts the preview at the end of the source's parent, so the selectors that match the source, including child combinators such as `.List > .Card`, also match the preview. The source's siblings keep their `:nth-child` positions, unless a live reorder moves one of them after the preview. This extra sibling has two side effects during the drag:

- Selectors that count from the end, such as `:last-child` and `:nth-last-child`, shift by one.
- DOM queries over the source's parent include it, such as `list.children`, `tbody.rows`, or `list.querySelectorAll('.Card')`. Exclude the preview with `:not([data-drag-preview])` when measuring.

Pass `container` to insert the preview somewhere else. It accepts an element, a ref, or a function that receives the source element:

```tsx title="Rendering the preview outside the list"
<Draggable.Preview container={(source) => source.closest('.Board')}>{label}</Draggable.Preview>
```

Pick the closest container that works. Outside the source's ancestors, descendant selectors such as `.Column .Card` stop matching the preview. Rules based on its own classes still apply.

### Drag cursor

During a mouse or pen drag, Base UI sets the cursor to `grabbing` over the whole document, whatever is under the pointer. Pass a different CSS cursor as `dragCursor`, or `false` to manage the cursor yourself. Set the resting cursor in your own styles:

```tsx title="Changing the drag cursor"
<Draggable.Root kind={card} payload={id} dragCursor="move" />
```

```css title="The resting cursor"
.Card {
  cursor: grab;
}
```

Base UI injects the cursor rule as a `<style>` element. See the [CSP guide](/react/utils/csp-provider) if your content security policy disallows it.

### Styling the source and preview

`[data-dragging]` is present on the source element during the drag. The clone never gets it, so a rule that dims the source leaves the preview intact. `[data-drag-preview]` is present on the preview only. That's the clone, or the element `<Draggable.Preview>` renders around custom children:

```css title="Dimming the source"
.Card[data-dragging] {
  opacity: 0.4;
}

.Card[data-drag-preview] {
  box-shadow: 0.25rem 0.25rem 0 rgb(0 0 0 / 12%);
}
```

With Tailwind CSS, use the `data-[drag-preview]:` variant, such as `data-[drag-preview]:shadow-md`. Content returned by a [`registerSource`](#registersource) `render` function gets the attribute on its root element, or on a `<div>` around it when it has several.

Base UI prevents text selection on draggables and disables page scrolling during a drag. Avoid setting `touch-action` on the draggable or its handle, since it interferes with touch dragging. Set it on a wrapper instead.

#### Animating a drop

After a release, the preview receives `[data-ending-style]`, and Base UI keeps it mounted until the animations that state starts have finished. Add a `translate` transition that applies once `[data-ending-style]` is set to move the preview to the source's final position, or back to the source after a release outside every target. Without one, the preview ends where it was released, so an ending fade runs there. Before the release, Base UI holds off transitions on the preview's `translate`, so it never trails the pointer. A custom preview's own transition, such as a `transition: all` meant for hover effects, stays off for `translate` at the release too:

```css title="Settling into place"
@media (prefers-reduced-motion: no-preference) {
  .Card[data-drag-preview][data-ending-style] {
    transition: translate 200ms ease;
  }
}
```

The ending preview also has `[data-dropped]` after a drop on a target. Use it when a drop creates something rather than moving the source, such as an item dragged from a palette. The source stays where it was, so the preview should fade where it was dropped instead of flying back:

```css title="Fading out on a drop, sliding back otherwise"
@media (prefers-reduced-motion: no-preference) {
  .PaletteItem[data-drag-preview][data-ending-style] {
    transition: translate 200ms ease;
  }

  .PaletteItem[data-drag-preview][data-ending-style][data-dropped] {
    opacity: 0;
    transition: opacity 150ms;
  }
}
```

The source receives `[data-settling]` while the preview settles, so you can show it as an empty placeholder until the preview arrives. In a `className` or `render` callback, read `state.settling`. The source also keeps `[data-dragging]` until then, which `state.dragging || state.settling` matches:

```css title="Hiding the source until the preview arrives"
.Card[data-settling] {
  color: transparent;
}
```

A drop that moves an item to another list usually mounts a new source element there. Base UI finds it by its `payload`, so the preview moves onto it when the new element gets the same payload object. When the payload is rebuilt, such as an object that includes the item's list, pass the same `previewKey` to both elements. Without a match, the preview ends where it was released.

Base UI adds no animation of its own. Keep your transitions inside a `prefers-reduced-motion: no-preference` media query, as above, so users who ask for reduced motion don't get them.

### Drop position within a target

A target record's `getLocalPoint()` returns where the pointer is within that target, as a fraction of its size. In a target's own handlers, read it from `eventDetails.currentTarget`. Each axis is `0` at the left or top edge and `1` at the right or bottom edge. Use it when a drop means a value rather than the target itself, such as a time within a day column:

```tsx title="A drop that means a time"
<Draggable.Target
  accept={event}
  payload={day}
  onDraggableDrop={(eventDetails) => {
    const { y } = eventDetails.currentTarget.getLocalPoint();
    schedule(eventDetails.source.payload, day, y * MINUTES_PER_DAY);
  }}
/>
```

The value isn't clamped, because an outer target can have the pointer outside its own box while a nested target is under it. Clamp it yourself if your data needs it.

`canDrop` receives `getLocalPoint()` and `getSnappedLocalPoint()` too, so a target can accept a drop on part of its box only. Returning `false` lets an ancestor receive the drop elsewhere. For example, a folder row can take files over its middle and leave its edges to the list behind it, which reorders:

```tsx title="A folder that accepts files over its middle"
<Draggable.Target
  accept={file}
  canDrop={(context) => {
    const { y } = context.getLocalPoint();
    return y > 0.25 && y < 0.75;
  }}
  onDraggableDrop={(eventDetails) => moveInto(eventDetails.source.payload, folder)}
/>
```

When the target represents fixed intervals such as 15-minute slots or weekday columns, declare `snap` and read `getSnappedLocalPoint()` instead. It rounds the fraction to the nearest step and clamps it between `0` and `1`. `snap` sets a number of steps per axis, so you don't need the target's size in pixels.

Both ends are included, so 96 steps give 97 values. A drop in the lower half of the last slot reports `1`, which is the end of the day. Cap the result when `1` isn't a valid value:

```tsx title="A day column with 15-minute slots"
<Draggable.Target
  accept={event}
  payload={day}
  snap={{ y: 96 }}
  onDraggableDrop={(eventDetails) => {
    const { y } = eventDetails.currentTarget.getSnappedLocalPoint();
    // Capped so the last slot starts inside the day.
    const start = Math.min(y * MINUTES_PER_DAY, MINUTES_PER_DAY - 15);
    schedule(eventDetails.source.payload, day, start);
  }}
/>
```

`snap` also accepts a function that receives the drag `source`, for a step count that depends on the item.

When the user moves an element, the value to commit is usually where the element lands rather than where the pointer is. Pass `{ anchor: 'source' }` to snap the dragged element's top-left corner instead of the pointer:

```tsx title="Snapping the element rather than the pointer"
const { y } = eventDetails.currentTarget.getSnappedLocalPoint({ anchor: 'source' });
const start = Math.min(y * MINUTES_PER_DAY, MINUTES_PER_DAY - 15);
```

`snap` only changes the value this target reports. To snap the preview itself, use the [`snapToGrid` modifier](#constraining-movement).

### Nested drop targets

When targets are nested, the innermost one that accepts the drag receives the drop. Return `false` from `canDrop` to skip a target and let an ancestor receive the drop instead. In the demo, the frame accepts only the chart, so a note released over the frame lands on the canvas behind it.

An outer target's handlers still run while the pointer is over a nested target. Their `eventDetails.target` is then the nested target, and `eventDetails.currentTarget` is the outer one.

import { DemoNestedDropTargets } from './demos/nesting';

<DemoNestedDropTargets />

Returning `false` means "skip this target" rather than "block this area". A target nested inside it can still receive the drop. Return `'reject'` when a rule must block the drop everywhere within the target. No target inside it or above it receives the drop, so a release there ends with the `'outside-release'` reason. For example, a full column should reject cards even over the cards it already contains. A rejecting target receives `[data-rejected]` while the drag is over it:

```tsx title="Rejecting drops in a full column"
<Draggable.Target
  accept={card}
  canDrop={() => (column.cards.length < limit ? true : 'reject')}
  className="Column"
/>
```

```css
.Column[data-rejected] {
  border-color: red;
}
```

### Styling drop targets

Targets expose their state through data attributes:

- `[data-accepting]` is present on every target that accepts the current drag, from pickup until the drag ends. Use it to highlight every possible destination as soon as a drag starts.
- `[data-drag-over]` is present while the drag is over the target or one of its nested targets.
- `[data-drag-over-innermost]` is present only on the innermost target, which is the one that would receive the drop.
- `[data-rejected]` is present while `canDrop` returns `'reject'` for the current position.

```css title="Highlighting targets"
.Column[data-accepting] {
  outline: 2px dashed oklch(14.5% 0 0deg / 30%);
}

.Column[data-drag-over] {
  background-color: oklch(97% 0 0deg);
}

.Slot[data-drag-over-innermost] {
  outline: 2px solid oklch(14.5% 0 0deg);
}
```

`[data-accepting]` is based on `accept` alone. A target can carry it and still refuse the drop when `canDrop` runs.

Tracking these states re-renders the target as the drag moves. Set `trackDragOver={false}` on targets that don't use them, for example when every row of a long list is a target. Their handlers still fire and they still receive drops:

```tsx title="A target without drag-over feedback"
<Draggable.Target accept={card} trackDragOver={false} onDraggableDrop={handleDrop} />
```

### Native file drops

Base UI drags carry no `dataTransfer`, so they can't exchange data with other windows or applications. To accept files from the desktop, add native `onDrop` and `onDragOver` handlers next to `onDraggableDrop`. One target can handle both kinds of drop:

```jsx title="Accepting files from the desktop"
<Draggable.Target
  accept={card}
  onDraggableDrop={handleCardDrop}
  onDrop={handleFileDrop}
  onDragOver={allowFileDrop}
/>
```

### One element with two roles

Use the `render` prop to give one element two roles. For example, an item that accepts drops from other items:

```tsx title="A source that is also a target"
const item = Draggable.createKind<string>('item');

<Draggable.Root
  kind={item}
  payload={id}
  render={<Draggable.Target accept={item} payload={id} />}
/>;
```

Don't use this pattern to build a sortable list. `<Draggable.CollisionProvider>` handles that case, including the dragged item's own position and which side of an item the pointer is on. See [Sorting a list](#sorting-a-list).

The `render` prop combines the other parts too. A scrollable list that accepts drops can be both a target and a viewport:

```tsx title="A target that is also a viewport"
<Draggable.Target accept={card} onDraggableDrop={handleDrop} render={<Draggable.Viewport />} />
```

### Sorting a list

Use `<Draggable.CollisionProvider>` to reorder a group of draggables. Pass the same `kind` to the provider and to each `<Draggable.Root>` inside it. The provider reports which item is under the pointer, and your handlers decide where to insert the dragged item.

Update the order in `onMoveEnd`. There, `eventDetails.target.payload` identifies the item under the pointer, and `eventDetails.target.getLocalPoint()` tells which half of it the pointer is in. For a vertical list, a `y` above `0.5` means the bottom half. `eventDetails.target` is `null` when the drag was canceled, released outside the group, or released over the dragged item itself.

import { DemoSortableOnDrop } from './demos/sortable-on-drop';

<DemoSortableOnDrop />

To show an insertion indicator, compute the position in `onCollisionChange` and store it in state. Its `eventDetails` include the `previousTarget`, so you can skip updates when the position hasn't changed:

```tsx title="Tracking the insertion position"
function getPosition(target) {
  return (
    target && {
      id: target.payload,
      placement: target.getLocalPoint().y > 0.5 ? 'after' : 'before',
    }
  );
}

<Draggable.CollisionProvider
  kind={task}
  onCollisionChange={(eventDetails) => {
    const next = getPosition(eventDetails.target);
    const previous = getPosition(eventDetails.previousTarget);
    if (next?.id !== previous?.id || next?.placement !== previous?.placement) {
      setPosition(next);
    }
  }}
  onMoveEnd={(eventDetails) => {
    setPosition(null);
    if (eventDetails.target) {
      moveTask(eventDetails.source.payload, getPosition(eventDetails.target));
    }
  }}
/>;
```

By default, the provider measures each item's own element. Pass `collisionElement` to `<Draggable.Root>` to measure a wrapper instead, for example a padded row so that the gaps between items count too. An empty list has no item to collide with, so render a `<Draggable.Target>` for it.

### Sorting while dragging

To move items during the drag, update the order in `onCollisionChange` instead of `onMoveEnd`. Compare `eventDetails.location.current.input` with `eventDetails.location.previous.input` to place the item based on which way the pointer moved.

import { DemoSortableLive } from './demos/sortable-live';

<DemoSortableLive />

Save the original order in `onMoveStart`. In `onMoveEnd`, restore it when `eventDetails.reason` isn't `'drop'`, which means the user canceled the drag or released it outside any target. A release over the dragged item itself has the `'drop'` reason but a `null` target. Keep the current order in that case.

When items animate into their new positions, pass `collisionElement` to measure a wrapper that stays still during the animation. For long lists, memoize the items and keep their handlers stable so that a reorder only moves DOM nodes.

Both demos let the keyboard reorder the focused item with <kbd>Alt</kbd>+<kbd>↑</kbd> and <kbd>Alt</kbd>+<kbd>↓</kbd>.

### Auto-scroll direction

CSS decides which axes can scroll. With `overflow-x: auto` and `overflow-y: hidden`, only horizontal scrolling is possible. To restrict it further, cancel a direction in `onDragScroll`. Base UI calls the handler once per direction on every scrolling frame:

```tsx title="Horizontal only"
<Draggable.Viewport
  onDragScroll={(eventDetails) => {
    if (eventDetails.direction === 'vertical') {
      eventDetails.cancel();
    }
  }}
/>
```

import { DemoDragAutoScrollAxis } from './demos/scrolling-axis';

<DemoDragAutoScrollAxis />

The keyboard moves the focused stop with <kbd>Alt</kbd>+<kbd>←</kbd> and <kbd>Alt</kbd>+<kbd>→</kbd>.

The handler's `eventDetails` also carry the drag `source`, so the allowed direction can depend on what's being dragged. A grid can scroll vertically for rows and horizontally for columns:

```tsx title="A direction that depends on the item"
<Draggable.Viewport
  accept={[row, column]}
  onDragScroll={(eventDetails) => {
    const allowed = row.matches(eventDetails.source) ? 'vertical' : 'horizontal';
    if (eventDetails.direction !== allowed) {
      eventDetails.cancel();
    }
  }}
/>
```

### Auto-scroll speed

`maxSpeed` sets the auto-scroll speed reached at the container's edge, in pixels per second. It defaults to `900`. Scrolling speeds up as the pointer gets closer to the edge. It also ramps up from zero over the first 400 milliseconds after the pointer enters an edge zone. Lower `maxSpeed` for a short list or raise it for a large scroll range:

```tsx title="Slower in a short list"
<Draggable.Viewport maxSpeed={300} />
```

It also accepts a function, which Base UI calls on every scrolling frame:

```tsx title="A speed based on the content height"
<Draggable.Viewport maxSpeed={({ element }) => Math.min(2400, element.scrollHeight / 4)} />
```

A `maxSpeed` of `0` stops the container and lets an ancestor scroll instead, the same as canceling in `onDragScroll`.

### Auto-scroll outside the viewport

`overflowMargin` lets scrolling continue when the drag moves outside a container. Pass one distance in CSS pixels for every edge, or an object with `top`, `right`, `bottom`, and `left` to set each edge separately:

```tsx title="Keep scrolling above and below a calendar"
<Draggable.Viewport overflowMargin={{ top: 160, bottom: 160 }} />
```

The default is `0`. Base UI treats omitted edges, negative values, and non-finite values as `0`. With only `top` and `bottom` set, the drag must stay between the viewport's left and right edges to keep scrolling. To include the corners, extend `left` and `right` too:

```tsx title="Extend every edge"
<Draggable.Viewport overflowMargin={80} />
```

The margin applies only after the drag enters the viewport. A drag that starts in the margin doesn't scroll the viewport. A drag that moves beyond the margin has to enter the viewport again. It also has to enter again after the viewport was `disabled` or didn't `accept` the drag.

Inside the viewport, the edge zones and speed work as usual. In the margin outside an enabled edge, scrolling runs as if the pointer were on the edge itself. It keeps the same 400ms ramp and tops out at `maxSpeed`. Scrolling stops beyond the margin.

Viewports that contain the drag position claim each scroll direction first. Viewports whose margin contains it then take the remaining directions, innermost first. Scroll limits still apply, and so do `cancel()` and `consume()` in `onDragScroll`. Drag modifiers still affect which viewport can scroll, as they do without margins.

The margin affects only auto-scrolling. It doesn't enlarge drop targets, move the preview, or change the coordinates passed to `onDragScroll`. It also doesn't affect page scrolling, which already continues when a captured pointer leaves the window.

### Custom auto-scrolling

When Base UI can't scroll an element itself, for example a canvas panned with a CSS `transform`, use `onDragScroll` to apply the movement yourself. The element doesn't need scrollable `overflow`. Edge zones, acceleration, and nesting work the same as for a scroll container.

import { DemoDragAutoScrollCanvas } from './demos/scrolling-canvas';

<DemoDragAutoScrollCanvas />

Render the viewport on the element that clips the canvas, not on the transformed content. In the handler, call `cancel()` to skip the default scroll, apply the movement, and call `consume()` to claim that direction so no ancestor viewport scrolls on it:

```tsx title="A canvas that pans itself"
<Draggable.Viewport
  onDragScroll={(eventDetails) => {
    eventDetails.cancel();
    camera.current = { x: camera.current.x + eventDetails.x, y: camera.current.y + eventDetails.y };
    content.current.style.transform = `translate(${-camera.current.x}px, ${-camera.current.y}px)`;
    eventDetails.consume();
  }}
/>
```

`eventDetails.x` and `eventDetails.y` are the distances Base UI would have passed to `scrollBy()` this frame, in pixels. A positive `x` moves the view right, so the content moves left. Apply them synchronously, through a ref rather than React state, because Base UI looks for drop targets again on the next frame.

The handler runs once per direction, with the other axis set to `0`. When the canvas reaches a bound, skip `consume()` so an ancestor can scroll instead:

```tsx title="A canvas with bounds"
<Draggable.Viewport
  onDragScroll={(eventDetails) => {
    eventDetails.cancel();
    const moved = panBy(eventDetails.x, eventDetails.y);
    if (moved.x || moved.y) {
      eventDetails.consume();
    }
  }}
/>
```

### Typed wrapper component

The wrapper below forwards its props to `<Draggable.Root>` for items of any kind. Type the props with `Draggable.Root.Props<Payload>`, which keeps `payload` required whenever the kind declares one. Don't use `React.ComponentProps<typeof Draggable.Root>`. It sets `Payload` to `unknown`, which no kind matches. Give `Payload` a default of `undefined`, as the component does, so the wrapper also works without a kind:

```tsx title="A wrapper for items of any kind"
import * as React from 'react';
import { Draggable } from '@base-ui/react/draggable';

export function SortableItem<Payload = undefined>(
  props: Draggable.Root.Props<Payload>,
): React.JSX.Element {
  return <Draggable.Root {...props} />;
}
```

A wrapper that destructures its props can't forward the rest as is. While `Payload` is generic, TypeScript can't tell whether `payload` is required. Declare `kind` and `payload` explicitly in that case. The wrapper then requires both, so pass `payload={undefined}` for a kind without a payload:

```tsx title="A wrapper that adds a handle"
export function SortableItem<Payload>({
  children,
  ...props
}: Draggable.Root.Props<Payload> & {
  kind: Draggable.Kind<Payload>;
  payload: Payload;
}): React.JSX.Element {
  return (
    <Draggable.Root {...props}>
      <Draggable.Handle>
        <span aria-hidden="true">⠿</span>
      </Draggable.Handle>
      {children}
    </Draggable.Root>
  );
}
```

A generic `<Draggable.Target>` wrapper declares `accept` the same way, plus `payload` when the target has one. This holds whether it spreads or destructures its props:

```tsx title="A drop target for items of any kind"
export function Slot<Source, Payload>({
  children,
  ...props
}: Draggable.Target.Props<Source, Payload> & {
  accept: Draggable.Accept<Source>;
  payload: Payload;
}): React.JSX.Element {
  return <Draggable.Target {...props}>{children}</Draggable.Target>;
}
```

## createGlobalKind

`createKind` matches kinds by identity. A target accepts a source only if both use the same kind object, usually a constant they both import. That doesn't work when the source and the target live in code that doesn't share modules, such as a plugin loaded at runtime, a micro-frontend, or two copies of the same package on one page. `createGlobalKind` uses a string key as the identity instead. Two calls with the same key, from anywhere on the page, return kinds that match each other:

```tsx title="The same kind declared in two separate bundles"
// In the host application
const card = Draggable.createGlobalKind<CardPayload>('myapp/card');

// In a plugin bundled separately
const card = Draggable.createGlobalKind<CardPayload>('myapp/card');
```

Keys are shared by the whole page, so a bare name like `'card'` could collide with a kind from another library. Prefix keys with your app or package name. Both sides must also agree on the payload type. TypeScript can't check that across bundles, so a mismatch only shows up at runtime.

Prefer `createKind` whenever the source and the target can import the same constant.

<TypesDraggable.createGlobalKind hideDescription />

## anyKind constant

A kind that matches every drag. Pass it to a target's `accept` prop to accept everything. The resulting `source.payload` is `unknown` until you narrow it with a specific kind's `matches` method.

`anyKind` only works in `accept`. `<Draggable.Root>`, `<Draggable.Preview>`, and `<Draggable.CollisionProvider>` can't take it as their `kind`, because each of them declares one specific kind.

```tsx title="Accepting every drag"
<Draggable.Target
  accept={Draggable.anyKind}
  onDraggableDrop={(eventDetails) => {
    if (card.matches(eventDetails.source)) {
      archive(eventDetails.source.payload);
    }
  }}
/>
```

## useActiveDrag

Returns the source of the drag in progress, or `null` when no drag is active. The calling component re-renders when a drag starts or ends, when the source's payload or drag data changes, and when the source moves to a new element. It doesn't re-render as the pointer moves. It works anywhere on the page, with or without a `<Draggable.Provider>`.

The returned object is a copy, so it isn't equal to the `eventDetails.source` that handlers receive. Compare payloads instead of the objects.

Pass a kind, or an array of kinds, to observe only those drags and type `source.payload`. Other drags return `null`.

```tsx title="Reading the active drag"
const anyDrag = Draggable.useActiveDrag();
const cardDrag = Draggable.useActiveDrag(card);
```

<TypesDraggable.useActiveDrag hideDescription />

## useMonitor

Observes drags anywhere on the page without an element or a `<Draggable.Provider>`. Use it for status indicators, analytics, or handling drops in one place.

Pass `accept` to filter by [kind](#kinds-and-payloads) and infer the type of `eventDetails.source.payload`. Omit it to observe every drag with an `unknown` payload.

```tsx title="Reacting to every stage of a drag"
Draggable.useMonitor({
  accept: card,
  // Fires once when a matching drag starts.
  onMoveStart: (eventDetails) => console.log('picked up', eventDetails.source.payload),
  // Fires when the drop targets under the pointer change.
  onTargetChange: (eventDetails) => console.log('over', eventDetails.target?.payload ?? 'nothing'),
  // Fires as the pointer moves, at most once per animation frame.
  onMove: (eventDetails) => console.log('at', eventDetails.location.current.input.clientX),
  // Fires once when the drag ends.
  onMoveEnd: (eventDetails) => {
    if (eventDetails.target) {
      console.log('dropped', eventDetails.source.payload, 'on', eventDetails.target.payload);
    }
  },
});
```

Monitors support the same handlers as `<Draggable.Root>`, except `onBeforeMoveStart`. A monitor mounted during a drag observes the remaining events, so `onMoveEnd` can fire without a preceding `onMoveStart`.

<TypesDraggable.useMonitor hideDescription />

## useManager

Returns the page-wide drag manager. Use it to register existing DOM elements as drag sources, drop targets, or scroll containers. The hook requires a `<Draggable.Provider>` above the calling component.

Each `useManager` call returns a stable manager for that hook instance. All managers share the page's drag session, so `cancelDrag()` ends the active drag whichever feature started it. Use distinct [kinds](#kinds-and-payloads) to keep unrelated features apart.

```tsx title="Getting the manager"
const manager = Draggable.useManager();
```

`registerSource`, `registerTarget`, and `registerViewport` take an element and a function that returns its options. `registerMonitor` takes only the options function. Each method returns a cleanup function, so register in an effect and return the cleanup:

```tsx title="Registering from an effect"
React.useEffect(() => {
  return manager.registerSource(element, () => ({ kind: card, payload: id }));
}, [manager, id]);
```

The manager and its methods are stable, so you can list them as effect dependencies. Base UI reads each option at these times:

| Option                                                  | When it's read                                                                        |
| :------------------------------------------------------ | :------------------------------------------------------------------------------------ |
| Event handlers and predicates, such as `canDrop`        | Every time they're needed, so they see the latest closure.                            |
| A source's `kind` and preview settings                  | Once when a drag starts. `preview.render` runs again on each `renderPreview()`.       |
| A source's `payload`                                    | At pickup, and whenever it changes during the drag.                                   |
| A target's `kind` and `payload`                         | Each time the target is evaluated, including on drop.                                 |
| `disabled`, `handle`, and the styles applied while idle | At registration and on the next `pointerdown`. Re-register to apply a change at once. |

### registerSource

Registers a drag source. `kind` is required here. It accepts the options of [`<Draggable.Root>`](#root) except `collision`, `collisionElement`, `collisionPayload`, and `snap`. It also takes `handle` to restrict pickup to an element, and `preview` to configure the preview:

```tsx title="Registering a source"
manager.registerSource(element, () => ({
  kind: card,
  payload: id,
  handle: handleRef,
  preview: { offset: 'pointer' },
}));
```

`preview` takes the options of [`<Draggable.Preview>`](#preview). Pass a `render` function instead of children to show custom content:

```tsx title="A custom preview for a registered source"
manager.registerSource(element, () => ({
  kind: card,
  payload: id,
  preview: {
    render: ({ source }) => <span className="Chip">{source.payload}</span>,
    offset: 'pointer',
  },
}));
```

### registerTarget

Registers a drop target. It accepts the options of [`<Draggable.Target>`](#target), except `trackDragOver`, since there is no React state to update. `accept` is required here.

```tsx title="Registering a target"
manager.registerTarget(element, () => ({
  accept: card,
  onDraggableDrop: (eventDetails) => moveCard(eventDetails.source.payload),
}));
```

TypeScript infers `eventDetails.source.payload` from `accept` but can't infer the target's own `payload` through the options function. Pass both type arguments, as in `registerTarget<typeof card, SlotPayload>`, when the target reads `eventDetails.currentTarget.payload`.

### registerViewport

Registers a scroll container, with the options of [`<Draggable.Viewport>`](#viewport). Use it to [scroll the page](#scrolling-the-page), or for a container rendered by code you don't control:

```tsx title="A container that appears later"
// Keep the element in state so the effect runs again once it exists.
const [scrollElement, setScrollElement] = React.useState<HTMLElement | null>(null);

React.useEffect(() => {
  if (!scrollElement) {
    return undefined;
  }
  return manager.registerViewport(scrollElement, () => ({
    maxSpeed: 600,
    overflowMargin: { top: 80, bottom: 80 },
  }));
}, [manager, scrollElement]);

<DataGrid onReady={(api) => setScrollElement(api.getScrollElement())} />;
```

### registerMonitor

Registers a monitor with the options of [`useMonitor`](#usemonitor):

```tsx title="Registering a monitor"
manager.registerMonitor(() => ({
  accept: card,
  onMoveStart: (eventDetails) => setActiveId(eventDetails.source.payload),
  onMoveEnd: () => setActiveId(null),
}));
```

### cancelDrag

Ends the drag in progress. `onMoveEnd` fires with a `null` target and the `'imperative-action'` reason. It does nothing when no drag is active. Use it when a route change, a dialog, or a deleted record invalidates the drag:

```tsx title="Canceling on navigation"
const manager = Draggable.useManager();

React.useEffect(() => {
  return router.subscribe(() => manager.cancelDrag());
}, [manager]);
```
