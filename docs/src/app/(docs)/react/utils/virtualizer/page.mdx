# Virtualizer

<Subtitle>Renders only the visible items of a large list.</Subtitle>

## Anatomy

Import the component and place it inside the list of a component that supports virtualization:

```jsx title="Anatomy"
import { Virtualizer } from '@base-ui/react/virtualizer';

// prettier-ignore
<Combobox.List>
  <Virtualizer>
    {(item) => <Combobox.Item value={item}>{item}</Combobox.Item>}
  </Virtualizer>
</Combobox.List>
```

`<Virtualizer>` renders a window of the visible and overscanned items instead of the whole collection, and connects to the surrounding list so that keyboard navigation, scrolling, selection, and accessibility metadata keep working for items that are not mounted.

It can be used inside `<Combobox.List>` and `<Autocomplete.List>`, or on its own by passing the collection to its `items` prop.

## Rendering items

Pass the collection to the `items` prop on the list root, and use the virtualizer as the only item-rendering child of the list. Its `children` is a function that receives an item and its index in the filtered collection, and must return exactly one item component:

```jsx title="Rendering items"
<Combobox.Root items={items} itemToStringLabel={(item) => item.name}>
  {/* ... */}
  <Combobox.List>
    <Virtualizer getItemKey={(item) => item.id}>
      {(item) => <Combobox.Item value={item}>{item.name}</Combobox.Item>}
    </Virtualizer>
  </Combobox.List>
</Combobox.Root>
```

Grid mode is not currently supported.

Use `getItemKey` to provide stable identity when item values are objects or when TypeScript cannot infer the item type. For primitive values, you can instead declare the item type explicitly, such as `<Virtualizer<string>>`.

## Grouped collections

A grouped collection is an array of groups, each an object with an `items` array, as for the list components: a collection whose elements carry an `items` array is taken for a grouped one. Pass it as `items` together with `renderGroupHeader`, which renders the element carrying a group's name. Inside `<Combobox.List>` that element is `<Combobox.GroupLabel>`; the virtualizer wraps each group's rendered items in a `role="group"` element labeled by it, so `<Combobox.Group>` is not used. The virtualizer only knows a group by its `items`, so annotate the group parameter with your own group type to read anything else from it:

```tsx title="Grouped items in a Combobox"
<Combobox.Root items={groups} itemToStringLabel={(item: Produce) => item.name}>
  {/* ... */}
  <Combobox.List>
    <Virtualizer
      getItemKey={(item: Produce) => item.id}
      getGroupKey={(group: ProduceGroup) => group.value}
      renderGroupHeader={(group: ProduceGroup) => (
        <Combobox.GroupLabel>{group.value}</Combobox.GroupLabel>
      )}
    >
      {(item) => <Combobox.Item value={item}>{item.name}</Combobox.Item>}
    </Virtualizer>
  </Combobox.List>
</Combobox.Root>
```

In a list of your own, the header renderer receives the group's name attributes as its third argument, to spread onto the element that names the group:

```tsx title="Grouped items in a custom list"
<Virtualizer
  items={groups}
  getItemKey={(item: Produce) => item.id}
  getGroupKey={(group: ProduceGroup) => group.value}
  renderGroupHeader={(group: ProduceGroup, groupIndex, headerProps) => (
    <div {...headerProps}>{group.value}</div>
  )}
  role="listbox"
>
  {(item, index, itemProps) => (
    <div {...itemProps} role="option">
      {item.name}
    </div>
  )}
</Virtualizer>
```

Group headers are rows of their own: they are measured like items, and `estimatedGroupHeaderHeight` is the height assumed for a header before it is measured. It defaults to the static `estimatedItemHeight`, and accepts a function receiving the group and its index. Headers never feed the running average that refines the item estimate.

Item indexes count items only, across all groups, so `activeIndex`, `scrollToIndex`, `isItemDisabled`, and `aria-posinset` mean the same thing in a grouped collection as in a flat one. `getIndexAtOffset` answers a header's offset with the first item of its group; for an empty group, with the item that follows it, or the last item when nothing follows. It returns `null` only when the collection has no items, however many headers it renders.

Groups are identified by their index in the collection by default. Provide `getGroupKey` when a collection can be filtered: once a group drops out, the groups behind it would otherwise change identity. A group with no items renders its header.

The wrapper the virtualizer renders around a group spans only the rendered part of that group, so it is not intended for styling; style the header and the items instead.

## Styling

The virtualizer is the scroll container, so constrain its height or maximum height. Without a height constraint, every item is rendered and virtualization provides no benefit. In the [table layout](#tables), the same goes for the element around the table.

The `--total-size` CSS variable contains the estimated or measured height of the virtual content. It can be combined with `--available-height` from the positioner to keep the popup within the viewport:

```css title="Constraining the scroll container"
.Scroller {
  height: min(22.5rem, var(--total-size));
  max-height: calc(var(--available-height) - 0.5rem);
  overflow: auto;
}
```

CSS `scroll-padding-top` and `scroll-padding-bottom` on the scroll container are respected when keyboard navigation scrolls an item into view.

## Sizing items

`estimatedItemHeight` is the height used for items that have not been measured yet. It defaults to `32` pixels, and a static number is automatically refined with the running average of measured items. Pass a function receiving the item and its index to keep full control over per-item estimates.

`overscanPx` controls the extra pixel buffer rendered before and after the visible range. It defaults to the larger of 150px and the first item's estimated height. Even an explicit value of `0` keeps a minimum render buffer of one estimated row.

## Disabled items

The `disabled` prop only marks a rendered item as disabled, so it is unavailable while the item is outside the rendered window. Pass `isItemDisabled` to the list root instead — it is the predicate keyboard navigation uses, including for items that are not mounted. Its index argument is the item's index in the filtered and limited collection.

## Scrolling to an item

`actionsRef` exposes `scrollToIndex`, which scrolls an item into view by its index in the filtered collection, including when the item is outside the rendered window:

```tsx title="Scrolling to an item"
const virtualizer = React.useRef<Virtualizer.Actions>(null);

// prettier-ignore
<Virtualizer actionsRef={virtualizer}>{/* ... */}</Virtualizer>;

virtualizer.current?.scrollToIndex(500, { align: 'center' });
```

## Standalone lists

Pass the collection to the virtualizer's own `items` prop to window a list that Base UI does not provide. Nothing else is required, so the virtualizer can be dropped into any scrolling list:

```jsx title="Windowing a custom list"
<Virtualizer items={items} getItemKey={(item) => item.id} role="listbox">
  {(item, index, itemProps) => (
    <div {...itemProps} role="option">
      {item.name}
    </div>
  )}
</Virtualizer>
```

The third argument of `children` carries the item's accessibility and collection metadata — `aria-posinset`, `aria-setsize`, and `data-index`. Spread it onto the element that represents the item, so assistive technology reports the whole collection rather than the mounted window. Items rendered by a list's own item component, such as `<Combobox.Item>`, receive it automatically.

Set `activeIndex` to the item the list treats as active. The virtualizer keeps that item mounted even when it falls outside the rendered window, so it can hold focus or be referenced by `aria-activedescendant`, and scrolls it into view.

Whether an activation should scroll depends on what caused it, not on which item ended up active: a keypress should bring the item into view, while a highlight following the pointer must leave the viewport alone — the cursor is already there, and moving the list would slide the next item under it. So the activation carries that decision, alongside the alignment it wants:

```jsx title="Activating an item"
// A keypress: scroll it into view.
setActive({ index: nextIndex });

// Jumping to the end of the collection reads better resting against that edge.
setActive({ index: items.length - 1, align: 'end' });

// A hover: highlight without moving the list.
setActive({ index, scroll: false });
```

Passing a bare index is shorthand for `{ index }`, so `activeIndex={5}` activates and scrolls. Because the scroll travels with the index rather than in a prop of its own, the two cannot disagree, and re-rendering with an equal activation does not scroll again.

Everything a list root normally coordinates stays with your list: filtering, keyboard navigation, selection, and clamping `activeIndex` to the current collection.

## Tables

Set `layout="table"` to virtualize the rows of a `<table>`. The virtualizer then renders a `<tbody>` instead of a scrolling `<div>`, and the element the item renderer returns is the row itself: a `<tr>`, with the renderer's third argument spread onto it. The markup stays a table, so column widths from a `<colgroup>`, a sticky `<thead>`, and the table's own accessibility semantics keep working.

import { DemoVirtualizerTable } from './demos/table';

<DemoVirtualizerTable />

The scroll container is an element of your own around the table: the nearest ancestor with `overflow: auto` or `overflow: scroll`, which is also the element a `position: sticky` header sticks to. Constrain its height. The section is held in place by the scrollport and moved by a transform, the way a list's rows are, so the rows it has stay on screen while the scrollport moves and the next window is rendered. A second `<tbody>` rendered after it reserves the space of the rows outside the window. Use `border-collapse: collapse` on the table, or a zero `border-spacing`, since spacing would otherwise only be counted for the rendered rows.

Give sticky header cells a `z-index`: the section is positioned too, and comes later in the table, so without one it paints over them. This layout relies on `position: sticky` and `transform` applying to table row groups, which current browsers support.

The third argument of `children` carries the row's measurement along with its metadata, so it has to reach the `<tr>` element. It includes a `style` for a row kept mounted outside the window; add styles of your own through `className`, or merge them into the `style` it carries rather than replacing it.

Rows are identified by their index in the collection, so set `aria-rowcount` on the table and `aria-rowindex` on each row from the renderer's index, counting the header row, for assistive technology to describe the whole table rather than the mounted window.

Everything else works as it does in a list. `activeIndex` keeps the active row mounted outside the window, so it can hold focus while keyboard navigation moves through the collection; `actionsRef` scrolls to rows by index; and `scroll-padding-top` on the scroll container keeps a scrolled row clear of a sticky header. Content passed to `trailing` is rendered as rows after the section's reserved space, and a grouped collection renders its group headers as rows among the items, without a wrapper around each group.

## Third-party virtualizers

A third-party virtualization library can be used instead when your application already uses one, or needs behavior that `<Virtualizer>` does not provide. Set the `virtualized` prop on the list root to opt out of the built-in item indexing, and coordinate filtering, item indexes, scrolling, and accessibility metadata yourself. See [virtualized Combobox](/react/components/combobox#virtualized) for a complete example.
